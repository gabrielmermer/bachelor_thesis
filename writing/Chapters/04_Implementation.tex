\section{Prototype ideation}

% The first step in the process was to identify the type of tools
% that were going to be needed in the game. 
The most important choice for the game prototype is whether it should use 2-dimensional or 3D graphics. 
First argument for 2D was the development speed.
Adding the third dimension to the game environment adds an additional layer of complexity. That means usually a longer time is needed to create projects due to having to make more advances assets and dealing with more complex physics.

% Another thing that makes making 3D games more difficult is physics. The vast majority of games have some sort of physics implementation, be it collision detection, particle systems or force vectors.
% Making those calculations is something that becomes much harder when adding a third dimension. 

Another argument for a 2D game was input precision.
When it comes to input in games, one of the most important factors is how responsive and exact the controls are, since the player's actions should align with the player's expectations. Movement in a 2D space is easier to describe in words compared to 3D movement, especially if the camera is from the perspective of the player.

For those two reasons that choice was made to follow with a 2D game. The next step was figuring out what type of game should be made.

% 3D: Look to the upper left a bit and then move 10 steps forward



% This example illustrates that it might be difficult for the player to describe camera motions since 3-dimensional transforms are rather complex. 


% Not all the 3D games rely on a player-controllable camera. Many games have a fixed camera or don't let the player
% control the camera at all. Despite that the direction that was decided was 2D game environment. This decision came from faster ideation and faster navigation as described above.


% After making that choice, the next logical step is to think of potential suitable game ideas that would differ from each other and would make it possible to utilise the voice input.
The next phase of the work had an exploratory meaning. In Design Thinking, this corresponds to the Ideation part of the \textcite{DoubleDiamondDesign2005} approach.
The reason for following that approach instead of going straight into building the finished game is to verify if the game idea is worth executing in the first place. More often than not, it turns out that games that work on paper are not enjoyable or playable in real life.
One additional thing that the prototypes can accomplish is to increase the creative potential for making even better solutions.
Mind often sees connections while experiencing, meaning that after the prototypes are played through, there's a chance of a new idea, a variation or some insight to occur. 


To be able to verify this thesis, a quick iteration and implementation are key, being arguments for choosing 2D for this project.


All of these reasons are valid for making some prototypes. Fail quickly, and iterate would be the motto here. 
Because of this, three games got created:

The first idea that spontaneously emerged was making a small maze prototype. This type of game is straightforward, making it an ideal testing ground for voice interaction. In this game, the player navigated a red square through a maze with the goal of exiting it through blue doors.
Developing this prototype has been challenging due to technical difficulties in transporting player-made audio recordings to the back-end. 
Additionally, WhisperCPP has proven to be challenging to work with, and a wrapper for the Whisper API has become necessary.
After going over those technical issues, it became clear that this prototype is not the way to go for this game due to two main reasons.
Firstly, navigation on the 2D grid meant using numbers. The number 2 would often be interpreted as "to", causing the system to not understand the player. This type of edge case can be accounted for at least partially, but the next issue that came up was much more serious.
Navigation on a 2D plane via natural language can quickly become too abstract for the game to understand. 
The player may navigate by issuing various types of commands.
For instance, they can use directions such as up, down, and left. Another method would be using a positional system in X-Y coordinates.
Yet another approach would be the sides of the world.
On top of that, they could do it by describing the desired relationship to other elements of the environment (such as 2 spaces from the north wall).
The usage of natural way of speech, and there's bound to be a lot of ways that people approach navigation. The prototype can be, of course, limited to just a few of those ways, but then there would be no notable difference between that system and pre-existing solutions such as \textcite{Talon2017}.
On top of that such solution could also result in a lower immersion, feeling closer to piloting a machine with a set of commands instead of guiding your own body.
To take this argument to the extreme in there is nothing stopping the player from just commanding the game to move to the finish location.

% intro

The second idea for testing was a text-based adventure game.
The player would travel across different locations, performing actions inside them and solving puzzles. 
This prototype would have a potential for higher player immersion due to being closer to reading a book than playing an advanced 3D game. 

Given that the player would control the character directly, this could potentially lead to them voicing their commands in first person.
This effect could also potentially raise immersion, creating a similar effect that can be observed in tabletop RPG players controlling their characters.

The technical implementation was not difficult this time around, since the audio transport code was reused from the last prototype.
The development process was straightforward, and p5js gave no issues.
Compared to the first prototype, the audio transcription proved to have almost no issues or edge cases. That can be attributed to the fact that 
The actions in the prototype, e.g., "Pick up the key", are rather specific, making the tool call LLM to interpret them without much issue. The only issue was the fact that the Travel function expected capitalised location names as parameters, but WhisperCPP would transcribe the location names as lowercase. The fix turned out to be a very simple instruction in the tools.json file, which made the LLM aware of this capitalisation.

\subsection{Front-end}

The game is served as a static webpage running the p5js sketch served by the Python http server. 
The following engines got considered when making the choice:

\begin{itemize}
    \item Unity3D -- Powerful and flexible engine that was decided against due to it's overhead slowing down development.
    \item Godot -- Slightly smaller overhead than Unity but still would slow down game creation. 
    \item Pico8 -- Minimal game engine with a focus on speed of development at the cost of forced limitations. Was decided against due to its inability to process http requests
    \item LÖVE -- Another minimal engine with support for http requests. The reason why it got decided against was limited learning resources and support.
    \item CLI -- Potentially offers the fastest development due to not being an engine at all. The lack of support for graphics was the reason against it.
    \item PyGame -- Medium-sized complexity. Too large overhead for this project combined with scarce learning resources were the reasons to not choose it.
    \item p5js -- The selected engine. Minimal overhead combined with http requests support and a large online community. Aside from needing to write UI rendering logic no obvious downsides were observed. 

\end{itemize}

\subsection{Routing API}

This layer talked with other hosts and handled the user requests. It was written using FastAPI.
It's role was to coordinate the other API's to reduce the logic that would need to be handled by the front end as much as possible.
The reason for that was to keep the front-end as much game focused as possible.

\subsection{WhisperCPP}

A very reliable local audio transcription model developed by OpenAI and implemented in C++ for extra efficiency. 
The project required a manual build process to take the full advantage of the local GPU hardware.
It ships with an integrated API server, which was used for this thesis.

\subsection{WhisperCPP control API}

Due to a bug in the GPU build of WhisperCPP, it broke on every transcription request past the 2nd one.
This bug was proven to be undocumented and difficult to fix. 
The model would behave normally when used on a CPU, but the processing time was 20 times longer compared to the GPU.
A quick solution to this problem is an API layer that takes the user requests and restarts WhisperCPP on every request.
While not ideal, this has proven to be an effective method for avoiding this bug.

\subsubsection{ToolACE-2 model}

Tool calling is a technique that allows the llm to translate the user request into known software funcitons. For instance if the player says "let's travel to the store" the tool calling model would return a function $Travel(Store)$.
The way this is possible is due to the fact that the model is fed a list of possible functions alongside the user request text.
This model was fine-tuned for this specific role.
The reason why this model was chosen was that it ranked in the top 3 on https://gorilla.cs.berkeley.edu/leaderboard.html at the time of development.

The model was manually quantified to allow to be run on consumer GPU.
This process makes the models use less memory at the cost of their precision by reducing the decimal precision point in the neural network nodes.
